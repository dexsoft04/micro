# Runtime S3 制品兼容要求

旧键支持是持续维护的功能需求。升级框架后，只保存在旧键中的服务制品仍须可读取，使旧版本业务服务在宕机、容器重建后能够重新下载原版本制品。不能以取消旧键读取作为删除问题的修复方式，也不能要求用户重新部署或重新编译所有旧版本来完成升级。

## Store 服务的键格式

platform 的 `store` 角色显式使用 `LegacyKeyFormat()`：读取、写入和显式删除均只访问历史对象键。这样旧 Store 实例能读取新实例写入的内容，新实例也能立即读到旧实例覆盖后的值；回退不依赖对象迁移。即使另一种格式下存在同逻辑键的内容，Store 也不读取或修改它。历史格式的键碰撞行为保持不变。

`runtime` 角色及插件默认行为继续使用下文的当前键优先、旧键回退规则。`List` 接收和返回物理对象键，前缀不会被转换；旧 Store RPC 不支持新增的 `Blob.List`，混跑期间不能将该方法视为所有实例均已支持。

构造 BlobStore 只配置客户端，不自动写入探针对象；服务就绪与真实读写须分别验证。

## 键格式与读取规则

Runtime 使用 `build://<service>:<version>` 标识二进制，使用 `source://<service>:<version>` 标识上传的源码。S3 插件兼容两种对象键：

| 逻辑键 | 当前对象键 | 旧对象键 |
| --- | --- | --- |
| `build://service:v1.0.0` | `build/service/v1.0.0` | `build-service-v1-0-0` |
| `source://service:v1.0.0` | `source/service/v1.0.0` | `source-service-v1-0-0` |

- 优先读取当前键；只有明确不存在且两种键不同，才读取旧键。
- 权限错误、网络错误和服务端错误必须返回，不能用旧内容掩盖当前键读取故障。
- 兼容读取不迁移、不删除旧对象；新的写入继续使用当前格式。
- 两种格式均使用同一 namespace。未指定固定 bucket 时，namespace 是 bucket；指定固定 bucket 时，namespace 是对象路径前缀。
- 旧格式将连续的非英文字母、非数字字符替换为 `-`，沿用历史映射，不保证不同逻辑键之间唯一。

## 重启与显式删除

普通宕机或容器重启不触发制品清理。启动加载器通过 `Runtime.Build.Read` 获取原版本二进制；该入口使用本插件时，必须能够读取仅存在于旧键中的制品。对象、权限及认证仍须有效；读取兼容不保证所有启动故障都能恢复。

显式删除服务时，Runtime manager 清理其源码和二进制。本插件的 `Delete` 必须清理逻辑键对应的当前键及旧键：

1. 先删除旧键，再删除当前键，避免当前键删除成功后暴露旧内容。
2. 旧键删除失败且不是对象不存在时，返回错误并保留当前键；当前键删除失败同样返回错误。
3. 两种键相同时只删除一次；对象已不存在时允许重复删除。
4. `Delete` 成功后，在没有并发新写入的条件下，再次读取该逻辑键不能返回任何一种制品。

清理仅针对同一 namespace 下由该逻辑键推导出的两个精确对象键，不扫描、不批量迁移存储。Runtime 的服务删除与异步制品清理不是原子操作；上述成功约定指 BlobStore 的 `Delete` 返回成功，不能由服务删除 RPC 成功直接推定。

## 回归验收

- 仅保留旧键对象，重新创建读取客户端后仍能下载同一内容。
- 新旧对象并存时优先返回当前内容；当前键非不存在错误不得回退。
- 对仅当前键、仅旧键、新旧并存、均不存在四种状态，删除后均不可读取，且可重复删除。
- 源码与二进制、两种 bucket 布局均覆盖；任一删除请求失败不得误报成功，也不得因此暴露旧制品。
- 构建公共 micro 模块时，既有 GitHub SSH 重写带或不带末尾 `/` 均须保持该仓库使用 HTTPS，已有 Gitee 重写保持有效。
- 公共 Go 依赖依次尝试 `goproxy.cn`、`goproxy.io`、`direct`；任一代理返回 500 等错误仍须允许后续回退。

相关自动化用例位于 `plugin/s3/s3_test.go` 和 `service/build/golang/golang_test.go`。代理用例使用本地 HTTP 服务及本地 Git 仓库，无需访问公共代理。真实环境的旧版本容器重启仍须结合实际 cell 镜像、制品及认证独立验收。
